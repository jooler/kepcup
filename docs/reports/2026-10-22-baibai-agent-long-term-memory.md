## 1. 视频在说什么

### 1.1 核心论点

长期陪伴型 Agent（管家、顾问、编程助手）失败，往往不是因为模型不够强，而是 **记忆策略错了**：

- 错误直觉：上下文窗口很大 → 把全部历史原样塞进提示词。
- 结果：Token 成本暴涨；信息密度被稀释；出现「草垛寻针」——模型变慢、答非所问。
- **真正难点不是怎么存，而是怎么扔、怎么找。**

短任务（写代码、润色邮件）三五轮即可；长陪伴要跨月/年仍能唤醒「上次那件事」。全量重放历史在成本和注意力上都不可持续。

### 1.2 三层记忆（视频模型）

借鉴人脑分工，把记忆拆成互不越界的三层：

| 层 | 存什么 | 介质/形态 | 职责 |
|---|---|---|---|
| **短期记忆** | 最近几轮原始对话 | 滑动窗口，原样进提示词 | 语气连贯、指代消解（「它的底盘怎么样」里的「它」） |
| **实体画像记忆** | 硬事实：身份、偏好、禁忌 | 结构化键值 / 卡片；**禁止只靠向量** | 零容错召回（如坚果过敏、纯素） |
| **长期情景记忆** | 情绪、故事、模糊经历 | 语义切片 + 向量库 | 模糊联想召回（「我之前吐槽过压力大的那些事」） |

横向对比（视频原意）：

- 短期：保鲜、带词与联贯。
- 画像：保真、身份/偏好/禁忌，容错率接近零。
- 情景：保全温度与经历，走概率相似度。

### 1.3 运行时：乐高式提示词拼装

用户第 N 轮发消息时，**不要**把库里所有东西倒进模型。动态合成四块：

1. 系统提示（人设与规则）
2. 从画像层读出的结构化事实
3. 按当前问题语义检索出的情景切片
4. 短期滑动窗口贴在最底部

示例效果（视频模拟）：用户说「帮我规划周末聚餐」→ 回复同时用上「坚果过敏」（画像精确读）和「创业压力大」（情景模糊捞），再扣住当前问题。

### 1.4 工程：影子 Agent 与记忆自进化

- **前后台解耦**：前台只拼现成记忆、尽快流式回复（保 TTFT）；后台「影子 Agent」异步抽事实、切片、写向量——类似睡觉时整理白天经历。
- **冲突与新陈代谢**：不能只盲写。例：旧「住北京」vs 新「搬到上海」→ 识别矛盾、更新/ supersede，并对过时噪音做遗忘退火，避免库越跑越脏。

### 1.5 三条「黄金法则」（视频收束）

1. **分层存储、各司其职**：短期滑窗 / 实体卡片 / 向量切片物理与职责分离，避免混存污染。
2. **精准检索、动静分离**：硬事实走结构化查询；弱语境走向量。硬事实不进概率空间赌召回。
3. **动态更新、保持清洁**：增量写入 + 冲突修订 + 遗忘退火 + 再挂载进新交互。

## 2. KepCup 现状（对照基线）

权威设计见 [04-memory.md](../design/04-memory.md)。实现落在 `packages/core/src/memory/`（`reflection`、`consolidation`、`retrieve`、`profile-curation`、`manager` 等）。

### 2.1 分层方式（与视频不完全同构，但同向）

| KepCup | 大致对应视频 | 说明 |
|---|---|---|
| 对话短期上下文 / 任务压缩（D93 等宿主侧） | 短期滑窗 | 宿主维护近期轮次；任务侧有自研压缩，不全靠「全历史」 |
| **共享用户画像** + 编译后的 **画像卡片**（约 400 token 常注入） | 实体画像 | 结构化 `MemoryItem`（fact / preference / …），画像整理 loop 合并冲突 |
| **Bot 私有记忆**（commitment / feedback / episode / lesson / …） | 部分画像 + 部分情景 | 关系与自我状态；episode 偏里程碑 |
| **相关记忆 top-k**（关键词 + 向量混合 / RRF） | 情景模糊召回 | 每次按触发消息检索注入（约 600 token 预算） |
| Wiki / Skills | 视频未展开 | 世界知识与流程刻意不进「用户记忆」 |

另有：显式 `remember`、事后 **反思 loop**、定期 **consolidation**、`superseded` / `retracted`、敏感与凭据过滤、用户「Bot 大脑」可控。

### 2.2 已对齐视频的部分

- **不是全量历史灌模型**：有预算注入（画像卡片 + top-k + 状态等），符合「乐高拼装」而非草垛。
- **硬事实有结构化路径**：画像条目 + 卡片，不是「全部向量化」。
- **异步沉淀方向**：反思在响应/任务结算后登记，不把整套抽取塞进 TTFT 主路径（设计意图；实现上纯对话去抖仍有缺口）。
- **冲突与代谢**：画像整理优先级（明确 > 推断、新 > 旧）；`supersedes`；定期合并/过期/淡化。
- **检索动静分离雏形**：画像卡片常驻 + 混合检索 top-k；工具可按需 `get_user_profile` / `recall_memory`。

### 2.3 与视频的差异（不是缺陷，是产品选型）

| 维度 | 视频 | KepCup |
|---|---|---|
| 主轴 | 单 Agent 三层（短/画像/情景） | **共享用户画像 × 多 Bot 私有记忆**（协作产品） |
| 情景层 | 强调情绪/故事向量切片 | episode + 混合检索；Wiki 承接知识，不全塞记忆 |
| 影子流水线 | 明确「前台快出 / 后台影子」叙事 | 反思/整理已有，但产品话术与调度粒度不同 |
| 硬事实强约束 | 「过敏类零容错、禁止只靠向量」讲得很死 | 有结构化与敏感策略；**硬禁忌是否每次无条件强注入**仍可更硬 |

## 3. 是否要「按视频大改」？

**不建议。** 视频是教学向的架构叙事，KepCup 在设计文档与代码上已经覆盖同一套工程问题（分层、预算注入、异步沉淀、冲突、检索）。推倒换成「标准三层 Demo」会丢掉多 Bot 共享画像、承诺与调度联动、Wiki/Skills 边界等产品资产。

值得做的是 **对照视频压力测试现有缺口**，做小步增强。

---

## 4. 建议增强（按优先级）

### P0 — 硬事实「手术刀」注入（对齐法则 2）

**问题**：过敏、禁忌、明确边界若只出现在 top-k 向量/关键词结果里，仍有漏召回风险。  
**方向**：

- 从画像中识别高敏 / 零容错类别（健康禁忌、明确「不要…」等，可复用 `sensitive-topics` 与 kind/sensitivity）。
- 每次组装上下文时 **无条件注入** 一小段「硬约束」块（与 ~400 token 画像卡片可合并或并列），不依赖本轮检索分数。
- 回归：构造「坚果过敏 + 请推荐甜点」类用例，断言回复不得推荐含坚果方案。

### P1 — 压缩 / 长任务前的记忆冲刷

**问题**：任务 Loop 压缩（D93）若丢掉尚未反思落库的事实，等于「扔错了东西」。  
**方向**：在 compaction / 长上下文丢弃前，触发或等待一轮轻量反思/冲刷，确保硬事实与承诺已进入记忆或画像提案队列。

### P1 — 纯对话反思去抖（设计已写、实现缺口）

`04-memory.md` 已记：纯对话应按去抖窗口登记，避免轮次膨胀后反思过密；现状多为 completed 对话轮各登记一次。  
**方向**：按设计补去抖窗口，降低成本与噪音，更接近视频「后台慢整理」节奏。

### P2 — 情景层体验（可选）

若产品要强化「陪伴温度」：

- 明确 episode 的切片粒度与向量召回评测集（模糊追问：「我之前说过压力大的那些事」）。
- 注入时区分「画像事实」vs「情景摘录」标签，避免模型把故事当硬约束。

### P2 — 可观测性

为记忆组装打结构化日志：本轮注入了哪些画像 id、哪些 retrieved id、是否命中硬约束块——便于对照视频里的「四模块拼装」做回归。

---

## 5. 明确不建议做的事

- 为了「对齐视频」把用户硬事实 **只** 存向量库。
- 取消共享画像、改成单 Bot 封闭记忆（与项目组 / 多 Bot 产品冲突）。
- 在主回复路径同步跑完整抽取 + embedding 写入（打爆 TTFT）。
- 把 Wiki/世界知识重新灌进记忆表「图省事」。

## 6. 一页对照表（速查）

| 视频主张 | KepCup | 动作 |
|---|---|---|
| 别全量塞历史 | 有预算注入与压缩 | 保持；盯压缩丢事实 |
| 短期滑窗 | 宿主近期上下文 | 保持 |
| 硬事实结构化、零容错 | 画像 + 卡片 + 条目 | **加强硬约束常驻注入** |
| 情景向量模糊召回 | 混合检索 top-k + episode | 可选加强评测与标签 |
| 影子异步沉淀 | 反思 / 画像整理 / consolidation | **补纯对话去抖**；压缩前冲刷 |
| 冲突更新与遗忘 | supersede、整理、淡化 | 保持；补冲突用例 |
| 三法则 | 设计同向 | 用法则做评审清单即可 |

---

## 7. 结论

白白说大模型这期把「长期记忆工程」讲成可执行的三层 + 拼装 + 影子流水线 + 自进化，和 KepCup `04-memory` 的方向一致。KepCup 的差异主要在 **多 Bot 共享画像** 与 **Wiki/Skills 分工**，这是产品优势，不是欠账。

**下一步（若立项）**：先做 P0 硬约束注入与测试，再补 P1 压缩前冲刷与反思去抖；不必单独立项「重做三层记忆」。相关设计增补可挂在 `docs/design/04-memory.md` 的修订节，或单独开 D-number 任务单。
