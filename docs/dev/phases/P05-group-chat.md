# P05 群聊

## 目标

用户可以创建群聊并与多个 Bot 对话：@ 或引用回复时由指定 Bot 响应；未指定时所有 Bot 先做轻量判断，要响应的按顺序执行，后执行者能看到前者的回复并可放弃；全员静默且有人认为“需要处理但不归我”时提示用户指定；Bot 之间只能通过明确 @ 触发，连锁受层数与预算限制。

## 范围

包含：

- 群聊的创建（选择成员、群名）、重命名、添加成员、移除成员、删除群聊。
- 右栏群信息：群名、成员列表（名片），点击进入某个 Bot 的详情；各 Bot 的授权列表。
- 输入框 `@`：弹出成员候选，键盘选择，以标签显示；草稿与消息存储结构化的 `mentions`。
- 引用回复：用户可以引用某条消息回复；引用 Bot 的消息等同于 @ 该 Bot。
- 分发器：目标确定、群聊判断、顺序执行、全员静默处理、新批次在轮次中的处理。
- Bot 之间的 @ 连锁：`send_message.mention_bot_ids`、层数上限 `BOT_CHAIN_MAX_DEPTH`、连锁预算、chains 表。
- 上下文：`<conversation_info>` 包含成员名片；其他 Bot 的发言包在 `<untrusted>` 中；顺序响应中后执行者的提示语。
- 平台规则 3、4。
- 界面：“正在确认由谁回复”“A 正在回复，B 排队中”；全员静默时的系统消息（可点击的 Bot 列表，点击即以 @ 该 Bot 的方式重新分发这一批消息）。
- 成员变动与删除 Bot 在群聊中的级联。

不包含：

- 群聊中的记忆分寸（来自私聊的记忆标注）在 P07 实现。

## 任务

1. **群聊领域**（`domain/groups.ts`）：创建时至少 2 个成员；成员来自通讯录；新加入的 Bot 无需特殊处理（查询工具本来就能读完整群历史）。
2. **分发器**（`dispatch/dispatcher.ts`），输入一批用户消息：
   1. 计算显式目标：批次中所有消息的 `mentions` 并集，加上被引用消息的发送 Bot（若为 Bot）。顺序按在批次中首次出现的先后。
   2. 有显式目标：按顺序依次投递（见下文“顺序执行”），`trigger_reason` 为 `mention` 或 `reply`。
   3. 没有显式目标：对群内所有 Bot **并行**做群聊判断（优先级 0，超时 `TRIAGE_TIMEOUT_MS`，超时视为 `no_action` 并记录日志）。
      - 判断为 `respond` 的 Bot 按 `confidence` 从高到低排序，依次投递，`trigger_reason = 'broadcast'`。
      - 没有 `respond`、且至少一个 `not_mine`：插入系统消息“没有 Bot 认领这条消息，请指定一个 Bot”，附成员列表。
      - 全部 `no_action`：不做任何事。
   4. “最近的对话对象”提示：最近一条 Bot 消息的发送者，以及该消息与本批次的时间间隔。
3. **顺序执行**（`dispatch/group-turn.ts`）
   - 一个“轮次”包含有序的目标列表；前一个 Bot 的执行结束（任何终态）后，才向下一个 Bot 的 Mailbox 投递。
   - 排在后面的 Bot 的触发段追加提示（[04-agent-runtime.md](../04-agent-runtime.md#触发段)）；前面 Bot 的回复已经是对话消息，自然出现在它的最近消息中。
   - 轮次进行中用户又发出新批次：
     - 正在执行的 Bot 通过注入收到新批次。
     - 轮次结束后，对新批次重新分发；已在本轮中执行、且执行期间已注入过该批次的 Bot 不再因该批次重复触发。
   - 轮次中某个 Bot 被删除或移出群：取消其执行，跳过，继续下一个。
4. **Bot 间连锁**（`dispatch/chains.ts`）
   - `send_message` 带 `mention_bot_ids` 时：校验被 @ 的 Bot 是群成员且不是自己；创建或延续连锁（`chainId` 继承自当前执行，没有则新建，`depth = 当前 depth + 1`）。
   - `depth > BOT_CHAIN_MAX_DEPTH` 时不触发，工具结果告知 Bot 已达上限。
   - 连锁预算：同一连锁累计 token 超过上限（常量 `BOT_CHAIN_TOKEN_BUDGET`，初始 200000）后不再触发。
   - 被 @ 的 Bot 以 `trigger_reason = 'chain'` 投递，优先级 1；它的触发段带 `from_bot` 与 `depth`。
   - Bot 的最终文本中的 `@名字` 不触发。
5. **成员移除**（`domain/lifecycle.ts`）：按 [03-data-model.md](../03-data-model.md#从群中移除-bot) 执行；删除 Bot 时一并删除其全部群成员行。
6. **界面**
   - 新建群聊对话框（选择成员，至少 2 个）；群设置（重命名、成员管理、删除群聊）。
   - `@` 候选弹层；引用回复入口（悬停消息时出现“引用”按钮）；输入区显示被引用消息的摘要，可取消。
   - 群聊的 Bot 状态行：判断阶段显示“正在确认由谁回复”；轮次中显示当前执行的 Bot 与排队的 Bot。
   - 已被移出群的 Bot 的历史消息，发送者显示其名字；已删除的 Bot 显示其 id。

## 接口与数据

- 新增表：`chains`。
- `constants.ts` 新增 `BOT_CHAIN_TOKEN_BUDGET = 200000`。
- RPC：`groups.create`、`groups.rename`、`groups.addMembers`、`groups.removeMember`、`conversations.members`；草稿接口增加 `mentions`、`replyTo` 参数。
- 事件：`group.turn`（轮次状态：判断中 / 当前 Bot / 排队列表）。

## 测试要求

- 单元：显式目标计算（多条消息的 @ 合并、引用 Bot 消息、引用用户消息不算目标、顺序）；判断结果排序；全员静默的三种情况。
- 集成（模拟模型服务，轻量模型负责判断）：
  - @ A → 只有 A 执行，没有判断请求发出。
  - 一批消息分别 @ A、@ B → A、B 按顺序执行，B 的上下文中包含 A 的回复。
  - 未 @：A `respond`（0.9）、B `respond`（0.6）、C `no_action` → A 先于 B 执行；B 调用 `skip_reply` 时不产生消息。
  - 未 @：全部 `not_mine` / `no_action` 混合 → 出现系统消息；全部 `no_action` → 无系统消息。
  - 判断超时 → 视为 `no_action`。
  - 点击系统消息中的 Bot → 以 @ 该 Bot 重新分发，该 Bot 执行。
  - A 用 `send_message` @ B → B 执行（`chain`，depth 1）；连锁超过 3 层停止；连锁预算超限停止。
  - 最终文本中写 `@B` 不触发 B。
  - 轮次中用户发新批次 → 当前 Bot 收到注入；轮次结束后新批次重新分发。
  - 轮次中移除排队中的 Bot → 被跳过；移除正在执行的 Bot → 执行取消，下一个继续。
  - 移除成员后其 workspace、授权、待确认审批被清理；再次加入后能用 `search_messages` 查到加入前的群消息。
- 端到端：创建群聊、@ 选择、引用回复、轮次状态显示、全员静默提示与点击指定。

## 验收标准

- [x] 群聊的创建、成员管理、删除可用；右栏显示群信息与成员。
- [x] @ 或引用 Bot 消息时，只有被指定的 Bot 响应，且不发出判断请求。
- [x] 未指定时，只有判断为要响应的 Bot 执行，并按顺序进行；后执行的 Bot 能看到前者回复，可以放弃。
- [x] 全员静默的提示逻辑与设计一致，点击提示中的 Bot 后由它响应。
- [x] Bot 只能通过 `send_message` 的 @ 触发其他 Bot，连锁不超过 3 层且受预算限制。
- [x] 界面清楚显示判断阶段、当前回复的 Bot 与排队的 Bot。
- [x] 成员移除、删除 Bot 的级联符合 03-data-model.md。
- [x] 新加入的 Bot 能读取完整群历史。
- [x] 群聊中绑定的 project 被所有成员共享，写入仍受租约保护（在 P04 之后执行时验证）。
- [x] 本阶段测试全部通过（迭代中跑定向测试，收口跑一次全量，见 [05-testing.md](../05-testing.md#开发中如何跑测试)）。

## 注意事项

- 群聊判断是单次结构化调用，不是完整 loop，不能调用工具。
- 判断请求并行发出，但仍受厂商并发上限约束。
- 不要从消息文本中用正则解析 @，只使用结构化的 `mentions`。
