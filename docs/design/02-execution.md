# 02 执行模型

## 基本原则

- Bot 每一次响应都是一个独立的 loop。
- 对话记录与执行 loop 分离：loop 的过程存入执行记录（Run），只有 Bot 发出的消息进入对话。
- Loop 在该 Bot 专属于该对话的 workspace 中工作：`{bot_id}/workspaces/{conversation_id}/`；对话绑定了 project 时，处理用户文件默认在 project 中进行。
- Loop 框架使用 pi，见 [09-tech-stack.md](09-tech-stack.md#agent-looppi)。

## 并发：每个“Bot + 对话”一个串行队列

- 每个“Bot + 对话”组合拥有一个串行消息队列（mailbox），同一时刻最多运行一个 loop。
- 这是 workspace 不冲突的真正保证：路径只隔离不同对话，同一对话内的并发由串行队列保证。
- **何时唤醒**：不做防抖。用户通过待发送队列自行决定何时发出，一批消息发出即唤醒 Bot，见 [01-conversation.md](01-conversation.md#输入与待发送队列)。
- **执行中收到新消息**：在 loop 的下一步注入（例如“你工作时对方又说了……”），由 Bot 决定调整方向还是继续。Loop 框架需要支持在每一步检查新消息。

## 执行记录（Run）

```text
Run
  id
  bot_id
  conversation_id
  loop_type
  trigger_message_ids[]
  trigger_reason        -- direct | mention | broadcast | scheduled | event ...
  status
  steps                 -- 工具调用与中间过程
  output_message_ids[]
  summary               -- 结束时生成的摘要
  continued_from_run_ids[]  -- 续接来源 run（Loop 续接），无续接时为空
```

- 每次 loop 结束都会留下执行记录和摘要。
- 应用退出或核心服务崩溃时，正在进行的 **ephemeral** 执行（默认，D49）标记为“中断”，重启后在对话中提示，**不自动恢复执行**；等待中的确认请求随之取消。标为 **durable** 的长任务按 journal 与工具 replay 策略恢复，见 [24-durable-execution.md](24-durable-execution.md)（D67）。

## Loop 续接

用户紧接着的下一句话常常是上一轮任务的延续（“还是按刚才那样改”）。每个 loop 独立启动，对话层上下文（摘要 + 最近消息）与 workspace 文件天然延续，但上一轮的**过程性上下文**（读过哪些文件、试过什么、为什么放弃）默认不进入新 loop。续接机制把这些过程记录回放进新 loop 的上下文：

- **原则**：续接 = 把同一“Bot + 对话”内最近若干次已结束 run 的过程记录注入新 loop；旧 run 的记录原样保留，不合并、不复制。反馈到对话的信息与状态（中间消息、状态行、最终回复、用量）只属于新 loop；落盘只落新 run，新 run 记录续接来源（`continued_from_run_ids`）。
- **与注入的关系**：执行中收到的新消息永远走注入（见“并发”）；续接只发生在“上一个 loop 已结束”的场景，两条路径不叠加。
- **候选范围**：同一（Bot, 对话）中已结束的响应 run（完成 / 失败 / 中断）；用户主动取消的 run 不作为默认续接对象，仅供判断模型选择。
- **默认续接（确定性）**：上一个候选 run 的结束时间距本次触发不超过 30 分钟时，直接回放该 run 的过程记录，不做模型判断。锚点是 **run 结束时间**，不是消息间隔（长任务可能跑了很久，“上一条用户消息”早已超窗）。
- **判断续接（轻量模型）**：不满足默认条件、但候选窗口内（24 小时）存在候选 run 时，由轻量模型做一次结构化判断：结合最近消息与各候选 run 的摘要，决定是否续接、续接哪些 run（可能为空）。判断失败或超时一律按“不续接”处理（fail-open）。
- **回放预算**：回放内容有独立 token 预算，优先保留最近的步骤；大段工具输出以占位符代替（workspace 常驻，需要时模型可重新读取）；超出预算从最早处截断并注明。
- **反思去重**：反思 loop 得知本次续接来源，不再对旧 run 已提炼过的事实重复提取记忆。

## Bot 如何发消息

- loop 结束时，模型的最终回复自动作为一条消息发出；最终回复为空时不发送。
- **中间说明自动投送**：loop 过程中，模型写在“带工具调用的回复”里的说明文字（如“收到，我先看看项目结构”）自动作为真实消息进入对话，让长任务有过程叙事；工具调用与工具输出本身仍只进执行记录，不进对话（todo/loop-interim-updates.md）。
  - 护栏：每个 run 最多投送 8 条（群聊 4 条），超出部分只记执行记录；单条超长（>2000 字符）截断。首次调用工具前说明打算怎么做、关键节点同步进展、其余工具调用不带文字，由 `<platform_rules>` 约束。
  - 进度不使用 `send_message`——中间说明直接写在回复文本里；`send_message` 保留给 @ 其他成员、发附件或主动分多条消息。
- 执行中途也可以通过 `send_message` 主动发送消息（确认收到、同步进展），一次执行可以发多条。
- 不需要回复时调用 `skip_reply` 结束执行（例如群聊中已经有人回答了）；此前已投送的中间消息保留。
- @ 其他 Bot 只能通过 `send_message` 的结构化参数；消息文本中的“@名字”不触发任何 Bot。
- 执行记录里保留全部中间过程（含未投送的说明文字）；Bot 下一次 loop 需要知道上次做了什么，可使用查询执行记录的工具。

## 缺设置的中断与续跑（inline setup）

功能依赖的配置缺失时，执行不是普通失败，而是**可引导的中断**（[18-inline-setup.md](18-inline-setup.md)）：

- 响应 run 执行开头检查模型可用性（Bot 指定 → 全局默认）：无可用模型时 run 以结构化 `setup={kind:'main-model'}` 失败，界面对话内呈现模型设置卡片。
- 能力模型未配置（如图像生成）时，对应工具返回 `SETUP_REQUIRED`，orchestrator 中断本 run 并改判为携带 `setup={kind:'capability-model', capability}` 的失败；普通失败横幅不出现，设置卡片取而代之。
- 用户在卡片内完成设置后，原 run 自动重试（触发消息照常），对话从中断处继续；用户主动发送但被模型门禁拦下的消息（草稿保留）也会在设置完成后自动发出。

## Loop 类型


| Loop       | 触发            | 可写入                                     | 优先级 |
| ---------- | ------------- | --------------------------------------- | --- |
| 响应         | 用户消息、定时、事件    | 消息、当前 workspace；另可提交记忆候选、Wiki 入库请求、定时任务 | 高   |
| 群聊判断       | 群消息未 @ 任何 Bot | 不写，仅返回判断结果                              | 高   |
| 反思         | 每次响应 loop 结束后 | 本 Bot 记忆、用户画像提案                         | 低   |
| 记忆整理       | 每天            | 本 Bot 记忆                                | 低   |
| 画像整理（全局唯一） | 收到画像提案、定期     | 共享用户画像                                  | 低   |
| Wiki 维护    | 入库队列、定期体检     | 本 Bot Wiki                              | 低   |
| 技能生成       | 反思建议、用户要求     | 本 Bot Skills（草稿）                        | 低   |


- 后台 loop 的工作目录为 `bots/{id}/maintenance/{loop_type}/`，与 `workspaces/` 分属不同命名空间，不会与对话 id 冲突。
- 后台 loop 永远不阻塞响应 loop。



## 上下文注入

每次响应 loop 按三层注入：

- **系统层**：Bot Profile（人设）、用户画像卡片、本 Bot 的相关记忆、我的状态、对话类型、群成员名单（含其他 Bot 的名片）、project 信息（见 [08-project.md](08-project.md#上下文注入)）、workspace 概况、Wiki 主题目录、Skills 列表。
- **对话层**：对话滚动摘要 + 最近 N 条消息，每条带发送者、时间、消息 id。
- **续接层**：按“Loop 续接”规则选出的历史 run 过程记录回放；没有续接时整段省略。
- **触发层**：本次触发的消息（可能为多条合并）及触发原因。

记忆相关的注入细则见 [04-memory.md](04-memory.md#注入方式)。

## 群聊响应



### 指定响应

- 用户 @ 了某个 Bot，或引用回复了某个 Bot 的消息：由被指定的 Bot 直接响应。



### 未指定时

1. 唤醒群内所有 Bot，各自先做一次**轻量判断**（只看最近几条消息，并带上“最近的对话对象”提示），结果为三种之一：
  - 要响应
  - 需要有人处理，但不归我
  - 不需要任何人回应
2. 判断为“要响应”的 Bot **按顺序执行**完整 loop；后执行的 Bot 能看到前者的回复，觉得已被回答可以放弃。
3. 所有判断结束（设超时）后，如果没有 Bot 响应，且至少一个 Bot 认为“需要有人处理但不归我”，则在对话中插入一条系统消息，附可点击的 Bot 列表，请用户指定。
4. 对“大家好”“谢谢”这类无需回应的消息，不弹出提示。
5. 按顺序响应的过程中，如果某个 Bot 被删除或移出群，其 loop 中断，跳过它继续下一个。



### Bot 之间的触发

- Bot 的发言默认不广播唤醒其他 Bot，只有明确 @ 另一个 Bot 时才触发。
- 设置最大连锁层数（例如 3 层）和总预算上限，防止无限循环。



## 主动消息

- 调度器支持两类触发：
  - **时间**：一次性或周期性。Bot 通过 `schedule(when, conversation_id, note)` 创建；带截止时间的承诺自动生成定时任务。
  - **事件**：异步任务完成、Wiki 入库完成、宿主层环境安装完成等，后续可接外部 webhook。
- 触发后以系统事件进入“Bot + 对话”队列，走正常的响应 loop；发不发、发什么由 Bot 决定。
- 护栏：免打扰时段、每日主动消息上限；用户可以查看并取消所有定时任务。
- 对话删除时，绑定该对话的定时任务一并取消。
- **错过的定时任务**：本地应用在电脑休眠或关机期间无法执行任务。唤醒后补执行，并在触发信息中告知 Bot 迟到了多久，由 Bot 决定是否仍要发送。



## 撤回与编辑

待发送队列中的内容尚未发出，用户可直接修改或删除，不产生任何事件。

已发出消息的撤回和编辑作为事件进入队列：


| 情况                 | 处理                     |
| ------------------ | ---------------------- |
| 正在运行的 loop 已读过     | 在下一步注入通知               |
| loop 已结束           | 编辑作为一次新触发，由 Bot 决定是否回应 |


撤回的连锁处理：

- 撤回的消息从 Bot 可见的历史中移除。
- 只以该消息为证据的记忆条目，由整理 loop 撤回。
- 撤回的附件如已入 Wiki，从 `raw/` 删除并重新体检。
