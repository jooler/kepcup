# 07 本地运行与环境

## 定位

- 本应用是**本地客户端应用**，不是云端服务。
- 支持平台：macOS、Windows（10 版本 19041 及以上、11）、Linux。
- 所有数据（对话、记忆、用户画像、Wiki、Skills、workspace）都存放在用户本机的 `~/.kepcup/`，见 [11-storage.md](11-storage.md)。

选择本地的理由：

- 记忆、用户画像、Wiki 是高度私人的数据，本地存放是核心卖点。
- 没有服务器成本。
- Bot 可以直接操作用户本机的 project 与 workspace。
- Claude Code、Codex 的技能生态本身面向本地环境。

## 进程结构

基于 Electron，详见 [09-tech-stack.md](09-tech-stack.md#桌面壳electron)。

| 进程 | 职责 |
|---|---|
| 主进程 | 托盘 / 菜单栏、窗口管理、启动并看护核心服务 |
| 界面进程 | 只负责显示与输入，可随时关闭 |
| 核心服务（Bot runtime） | 独立 Node 进程，常驻后台：串行队列、调度器、各类 loop、工具网关、环境管理器、数据库 |

- 界面通过 IPC 连接核心服务。
- 应用以托盘 / 菜单栏形式常驻，支持开机自启。关闭窗口后 Bot 仍在工作。

## 本地化的代价与应对

| 代价 | 应对 |
|---|---|
| 定时任务、主动消息要求应用在运行 | 核心服务常驻；休眠期间错过的任务按[补执行策略](02-execution.md#主动消息)处理 |
| 模型调用由用户付费，后台 loop 也消耗 token | 界面展示每个 Bot、每类 loop 的用量，支持设置预算 |
| 三个平台的沙箱机制各不相同 | 分级沙箱，见 [10-sandbox.md](10-sandbox.md) |
| 数据只在一台机器上 | 首版不做多设备同步和移动端，数据结构为日后同步留出余地 |

## 环境配置：分级、按需

原则：**能自带的都自带，其余在第一次用到时再准备；所有安装都放在应用私有目录，不修改系统全局环境。** 例外是沙箱所需的一次性系统授权（见下文“首次启动”）。

| 层级 | 内容 | 准备时机 |
|---|---|---|
| 自带 | 核心服务、数据库、内嵌 git 库（es-git）、`srt` 及其依赖（`rg`；Linux 上的 `bwrap`、`socat`）、Windows 的精简 Linux 根文件系统、浏览器工具（Electron 内置 Chromium） | 安装应用时 |
| 首次启动 | 模型 API key、开机自启与通知权限、沙箱能力检测与一次性系统授权 | 首次启动引导，只询问必需项 |
| 按需 | Python / Node 运行时、依赖包、git 命令行等工具、本地向量模型与 ONNX 运行库、增强沙箱、外部智能体（ACP 适配器 / 厂商 CLI，用户在设置页「智能体」启用时安装，D72，见 [28-external-agents-acp.md](28-external-agents-acp.md)） | 安装技能时解析依赖，或 Bot 执行中发现缺失（本地向量栈：首次记忆写入时由系统发起一张合并审批卡，含 `embedding-model` + `onnxruntime` 两个条目，型号与 GPU 选型见 [16-capability-models.md](16-capability-models.md)「向量来源的本地实现」） |
| 维护 | 环境体检、清理不再使用的运行时、应用升级时的数据迁移 | 启动时及定期 |

首次启动时各平台的沙箱准备：

- **macOS**：无需额外操作。
- **Linux**：检测用户命名空间是否可用；受 AppArmor 等限制时，引导用户执行一次 sudo 命令解除。
- **Windows**：引导启用 WSL2（需要一次管理员授权和一次重启），然后导入应用的私有发行版。可以跳过；跳过则在 Bot 首次需要执行代码时走申请流程。

其他：

- **Wiki、Skills、检查点的版本管理使用内嵌 git 库，不调用系统 `git` 命令**（例如 macOS 未安装开发者工具时，调用 `git` 会弹出安装对话框）。
- Bot 在 workspace 或 project 中需要使用 git 命令行时，git 命令行作为宿主层环境，走正常申请流程安装。

## 两层配置职责

Bot 本身是一个具备环境配置能力的 harness，但权限分两层：

### 宿主层

应用级、所有 Bot 共享的环境：运行时、git 命令行、本地向量模型、增强沙箱等。由核心服务中的**环境管理器**负责。

流程：

1. Bot 调用 `request_environment(需求, 原因)` 提出申请。
2. 对话中出现确认卡片，例如“我需要安装 Python 3.12 和 pandas，约 80MB，是否同意？”。
3. **每次安装都需用户确认。**
4. 安装完成后，作为事件进入该 Bot 的队列，Bot 继续工作。

### Workspace 层

Bot 在自己沙箱内的工作环境，例如在 workspace 中创建 Python 虚拟环境、安装 npm 依赖。Bot 在网络策略允许的范围内自由配置，无需确认。

## 环境清单与缓存

- 所有安装记录在数据库的环境安装记录中（环境清单），可复现、可清理。
- 依赖包按内容缓存，多个 workspace 共享，避免重复下载。

## 环境体检与降级

- 启动时及定期检查运行时、沙箱能力、磁盘占用。
- 沙箱不可用时，代码执行降级为逐条确认模式；其他能力不可用时，依赖它的技能和工具**直接禁用并说明原因**。绝不悄悄在无沙箱的情况下运行。
