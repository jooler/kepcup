# 13 访问授权（软隔离）

## 原则

- 与各类编程 Agent 一致：**默认范围小，越界时向用户申请授权，批准后继续。**
- 软硬结合：
  - **文件工具**（读、写、编辑、搜索、列目录）由工具网关按路径精确检查，越界即请求授权（软隔离）。
  - **命令行**在沙箱中执行，沙箱规则在每条命令执行前按当前授权实时生成（硬隔离）。命令可能间接访问任意路径，无法靠解析命令判断，因此不能只靠软隔离。

## 默认可访问范围

| 位置 | 默认 |
|---|---|
| 当前 workspace | 读写 |
| 当前对话的 project | 读写（写入需持有写入租约，见 [08-project.md](08-project.md#并发写入租约)） |
| 系统目录、工具链目录 | 只读 |
| 本机其他位置 | 读、写都需授权 |
| `~/.ssh`、系统钥匙串、`~/.aws`、`~/.config/gh` 等敏感位置 | 需授权，授权卡片醒目警告 |
| `~/.kepcup`（应用数据目录） | 永远不可授权 |

## 授权

```text
Grant
  id
  bot_id
  conversation_id
  path            -- 文件或目录
  access          -- read | write（write 包含 read）
  duration        -- once | conversation
  created_at
  revoked_at
```

- 授权**只给提出申请的 Bot，只在当前对话内有效**。群里其他 Bot 需要时各自申请。
- 有效期两种：
  - **仅这一次**：本次执行结束即失效。
  - **本对话内一直允许**：直到用户撤销。
- 没有永久授权。
- 用户可以在界面中查看当前对话的全部授权，随时撤销。
- 删除对话、删除 Bot、从群中移除 Bot 时，相关授权一并失效。
- 授权范围内的写入同样需要写入租约（按目录）。
- 可回退性：
  - 文件工具的写入在修改前逐文件备份，可以回退。
  - 命令行对授权目录的改动不保证可以回退，授权卡片中会注明。

## 流程

### 文件工具越界

1. 工具网关发现目标路径超出当前可访问范围，loop 暂停，对话中出现**授权卡片**：申请的 Bot、路径、读还是写、Bot 给出的原因。
2. 用户选择：仅这一次 / 本对话内一直允许 / 拒绝。
3. 批准后继续执行；拒绝时工具向 Bot 返回“用户拒绝”，由 Bot 自行调整做法。

- 即使用户在消息中明确要求处理项目外的文件，也仍然弹出授权卡片（一次点击即可），防止 Bot 误解路径。
- Bot 也可以在批量操作前主动调用 `request_access(path, access, reason)` 一次性申请。
- 等待授权期间 loop 处于暂停状态，不消耗 token；用户的新消息照常在下一步注入。

### 命令行

- 每条命令执行前，按 workspace、project（写入租约）与当前有效授权生成沙箱规则。
- 命令因沙箱限制失败时，沙箱会报告被拦截的路径；Bot 据此调用 `request_access` 申请授权，批准后重新执行。
- 命令的交互执行（交互模式、凭据注入）与各平台的降级规则见 [15-interactive-execution.md](15-interactive-execution.md)。

### 沙箱外执行

- Bot 可以调用 `request_unsandboxed(command, reason)`，申请在沙箱外执行某一条命令（例如需要调用 Docker、系统钥匙串的命令）。
- **每次都必须由用户确认**，没有“一直允许”；卡片显示完整命令并醒目标出风险。
- 沙箱外执行的改动不保证可以回退。

### 沙箱不可用时：逐条确认模式

- 当前机器上沙箱不可用时（例如 Windows 尚未启用 WSL2、Linux 尚未解除用户命名空间限制），代码执行**降级为逐条确认**：每条命令执行前都弹出确认卡片（显示完整命令），用户确认后才在沙箱外执行。
- 文件工具不受影响，仍按软隔离规则执行。
- 界面持续提示当前处于逐条确认模式及其原因。

“绝不悄悄在无沙箱的情况下运行”的原则不变：沙箱外执行只在用户对每一条命令明确确认，或用户主动开启无人值守模式后发生。

## 只读命令白名单

逐条确认模式下，白名单中的命令**无需确认**直接执行。沙箱可用时命令本就无需确认，白名单不起作用。

- 内置默认白名单只包含只读命令，例如 `ls`、`pwd`、`cat`、`head`、`tail`、`wc`、`file`、`stat`、`du`、`tree`、`which`、`grep`、`rg`、`find`，以及 `git status`、`git diff`、`git log`、`git show`。
- 严格匹配，以下情况不豁免：
  - 整条命令中有任何一段不在白名单中（管道、`&&`、`;` 连接的每一段都要命中）
  - 出现写入重定向（`>`、`>>`）、`tee`、命令替换（`$()`、反引号）、后台执行（`&`）、子 shell、变量赋值前缀
  - 带有写入或执行语义的参数，例如 `find -exec`、`find -delete`、`sed -i`、`git -c`
- 白名单不放宽访问范围：命令参数中的路径超出可访问范围时，仍需访问授权。
- 用户可以在设置中查看、增删白名单条目。自定义条目不一定是只读的（例如 `npm test` 会执行项目代码），添加时提示风险由用户承担。

## 无人值守模式

用户不在电脑前时，后台任务不会因等待确认而卡住。

- 开启后，**所有需要用户确认的操作一律自动批准**：访问授权、沙箱外执行、逐条确认模式下的命令、git 远程操作、宿主层环境安装、技能导入、凭据注入。例外（D73）：连接应用中风险为 `destructive` 的工具不自动批准，挂起等待用户（见 [29-connected-apps.md](29-connected-apps.md) §8.1）。
- 开启时弹框明确提示这是危险操作，并列出将被自动批准的操作类型（含凭据注入与命令交互输入的无人值守语义，见 [15-interactive-execution.md](15-interactive-execution.md)）；用户确认后生效。
- 凭据申请：本对话内已记住的凭据自动注入使用；没有可用凭据的申请自动拒绝并告知 Bot，绝不挂起。交互模式命令照常执行，无人在场输入时按空闲超时结束。
- 全局开关，可在设置和托盘菜单中切换；开启时可选择“手动关闭”或“N 小时后自动关闭”。
- 底线不变：应用数据目录 `~/.kepcup` 在无人值守模式下仍不可访问。
- 自动批准的访问授权按“仅这一次”处理，模式关闭后不遗留授权。
- 开启期间窗口顶部显示持续的醒目横幅，托盘图标同步显示状态。
- 自动批准的每一项都记入审计记录（Bot、对话、操作、时间）；用户回来或关闭模式时汇总展示。检查点照常生成，可以回退。

## 系统通知

非无人值守模式下，有待确认的操作且窗口不在前台时，发送系统通知。

## 界面

- 对话中的卡片：授权、沙箱外执行确认、逐条确认模式下的命令确认。
- 右栏显示当前对话中各 Bot 的有效授权列表，可以撤销。
