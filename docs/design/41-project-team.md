# 41 项目组（Project Team）：从群聊到协作空间

**状态：草案 v0.1（2026-10-17，待讨论）**。本文评估「把群聊升级为项目组」的想法，并结合代码现状给出首版方案；**尚未定稿**，不进 README 决策表，定稿后记为 D92。早期阶段，不背向后兼容的包袱，以当前代码逻辑正确为准。

相关：D4（群 `@` 连锁，[02](02-execution.md#群聊响应)）、D5（群顺序响应）、D28（Project 目录，[08](08-project.md)）、D60（群创建 / 群定位，[19](19-work-path-and-group-setup.md)）、D70 / D71（管家与委派，[27](27-butler-and-delegation.md)）、D75（对话轮与任务，[30](30-supervisor-and-tasks.md)）、D89（对话内设置，[38](38-conversational-settings.md)）、D90（工作台，[39](39-workbench.md)）、[12-ui-layout.md](12-ui-layout.md)、DEV-030（群定位无编辑入口，[DEVIATIONS](../dev/DEVIATIONS.md)）。

## 0 摘要

- **判断**：方向成立，而且和既有设计一致——D90 已经把心智模型写成「Bot = 员工、群 = 项目组、管家 = 助理」，本方案是把这句话从工作台推进到群本身。建议采纳，但有五处需要先调整或先决定（§2）。
- **最小改动路径**：不新增 `conversations.type`，不新增 Project 实体。**群聊就是项目组**：会话行是项目根，加一列 `lead_bot_id` 记负责人（可空）；「沟通」就是现有群聊，原样保留；其他模块的数据以后都以 `conversation_id` 为键挂在会话下。
- **负责人**是**项目内角色**（会话级属性），不是 Bot 属性、不是 `system_role`。本期它和成员的差别只有两点：未 `@` 任何人的用户消息**默认交给它**（取代广播判断）；提示词里带统筹职责。调度成员靠沟通里的 `@`（D4，连锁预算内），不新造 Bot→Bot 协议。
- **模块框架**＝ `shared` 里的纯数据注册表（模块 id / 状态 / 谁能写）+ 宿主强制的写权限声明 + 渲染层 tab 容器。本期只有「沟通」可用，看板 / 文档 / OKR / 日历登记为 `planned` 并在界面灰显。**不预建宿主侧插件接口**，等第一个写模块（看板）来驱动。
- **界面**：创建改双轮（先选 1 位负责人，再选成员）；顶栏改三段式（项目名 | 模块 tab | 成员 + 功能区）；右栏在群聊下撤除，其内容（含**访问授权撤销**这个安全控制）整体迁入「项目详情」弹框；顺带补上 DEV-030 缺的「项目目标」编辑入口。
- **读代码发现的一处缺口**：任务结算唤醒的对话轮**不继承** `@` **连锁**，隔一个任务就重置深度与预算，D4 的防环上限在宿主层被绕过（§5.3）。今天的群聊里就存在，负责人式调度会让它变成常态，建议并入本期修复。
- **最需要你确认或反驳的**：①现有群一律升级为项目组、不保留「纯群聊」形态；②未 `@` 的消息默认给负责人；③负责人在项目内的权力**不**套用 D90 的「仅用户本人触发」闸门；④「用户直接与负责人对话」落在沟通频道的默认路由，而不是另开一个负责人单聊；⑤修订连锁语义（上一条）。完整清单见 §12。

## 1 想法归纳

原始想法（用户 2026-10-17）：群聊源自人类社交场景，用户「拉群」的目的是**协作**（达成目标 / 维护状态），不是让 Bot 在群里聊天；应当升级为类项目协作软件的「项目组」。

| # | 内容 |
|---|---|
| R1 | 原群聊保留，更名「沟通」，作为项目组的一个功能块 |
| R2 | 增加看板 / 文档 / OKR / 日历等模块做信息对齐，项目内 Bot 均可见 |
| R3 | 指定或创建一个 Bot 为**项目负责人**：类似管家但权限限于项目组内；用户可直接与其对话，由其调度成员、管理各模块，也可参与「沟通」 |
| R4 | 权限：有调度能力的看板、OKR 等，负责人写；文档等信息同步类模块，全员读写 |
| R5 | 本期完成功能框架 + 沟通模块植入，其余模块下期 |
| U1 | 新建时中部选 Bot 的菜单改双轮：第一轮选 1 位负责人，第二轮选多位成员 |
| U2 | 项目组界面不再需要右栏详情 |
| U3 | 顶部 tab 切换：沟通 / 任务（看板）/ 文档 / OKR … |
| U4 | 项目设置本地目录，所有成员授权访问 |
| U5 | 右上角功能按钮区：管理成员、项目详情等（下拉菜单或弹框） |

## 2 评估

### 2.1 总体判断

**成立，且代码与设计已有铺垫**：

- D90 的 §1 已把群定位成项目组；工作台事项已能指派给「群 + 可选负责 Bot」（`TodoAssignee.group.leadBotId`），派发就是一条带结构化 `@` 的可见消息——「负责人」在数据结构里早有雏形，只是群本身没有这个角色（39 §2.2 明写「群没有负责人角色」）。
- 目录授权（U4）已经成立：目录绑在对话上，群内所有 Bot 读写（`conversations.project_id`，D28）。
- 现行群路由对「协作」其实是**负担**：每条未 `@` 的消息，群内每个 Bot 各做一次轻量模型判断（`GroupTurnCoordinator.#startTriage`，N 个成员 N 次调用），还可能出现「无人认领」（`group_no_claim`）。负责人默认路由直接消掉这两件事。
- 反过来，Bot↔Bot 的可见沟通在项目里**没有过时**：它是负责人调度的审计轨迹（谁被交代了什么、谁回了什么）。所以「沟通」降级为模块、不是删掉。

## 4 方案总览（拟决策）

| # | 拟决策 |
|---|---|
| P1 | **项目组 = 群聊的升级形态**：不新增 `conversations.type`、不新增实体；会话行即项目根，`conversations.lead_bot_id`（可空）记负责人。所有群一律是项目组（无负责人 = 暂未指定，行为同原群聊） |

## 5 数据与后端

### 5.1 实体

```sql
-- main 迁移 0038（ALTER TABLE，无需重建）
ALTER TABLE conversations ADD COLUMN lead_bot_id TEXT;   -- 项目负责人；NULL = 暂未指定
```

- **不设 FK**：Bot 删除是「bots 行改占位」，FK 不会触发；清理走 lifecycle，并有启动对账兜底（与 `assignee_group_id` 同款，见 [03-data-model](../dev/03-data-model.md)）。
- 不变式：`lead_bot_id` 非空 ⇒ 该 Bot 是 active 且在 `conversation_members` 里、不是管家。违反的一律清空（启动对账）。
- 单聊恒为 NULL。`Conversation` 契约增 `leadBotId: string | null`（可选字段，旧行缺省 null）。
- 项目目标沿用现有 `conversations.description`（界面叫「项目目标」）；创建时仍不收集，详情里可编辑（补 DEV-030）。
- 其余模块的数据以后各自建表，键为 `conversation_id`（= 项目 id），`ON DELETE CASCADE`。

**为什么不新增 type / 独立实体**（对照见附录 A）：新增 type 要重建 `conversations`，并改核心约 30 处、渲染 17 个文件里的判断，换来的只是一个「是不是项目组」的布尔；而「所有群一律是项目组」之后这个布尔不存在。独立 `projects` 实体在「一个项目一个沟通频道」的前提下只是多一层间接。将来若真要多频道，把现有会话 id 当项目 id、新增 `project_teams` 即可平滑过渡，所以现在不为它付成本。

### 5.2 角色与权限

| | 用户 | 负责人 | 成员 | 管家 |
|---|---|---|---|---|
| 发言 / 响应 | ✓ | ✓ 默认接收未 `@` 的用户消息 | ✓ 被 `@` / 被回复时响应 | 不在项目内（除非被拉进来当成员） |
| `@` 成员触发其响应 | — | ✓（D4，连锁预算内） | ✓（同 D4） | — |
| 改项目信息（名称 / 目标 / 目录 / 成员 / 负责人） | ✓ | ✗ | ✗ | 经 D89 设置卡，上限 `confirm` |
| 读模块 | 全部 | 全部 | 全部 | ✗ |
| 写模块 | 全部 | 注册表里 `write:'lead'` 的 | `write:'members'` 的 | ✗ |

**权力半径 = 项目组**：负责人没有建 Bot、跨项目委派、改别的 Bot 设置等能力；沙箱外执行、git 远程、敏感写入的用户审批仍照常出卡，不因身份豁免。

### 5.3 沟通路由（P4）

`GroupTurnCoordinator.#dispatch` 的决策顺序：

```text
forcedTarget 非空                         → 该 Bot（工作台派发，现有）
explicitTargets(...) 非空                 → 这些 Bot（@ / 回复，现有）
leadOf(conversationId) 是 active 成员     → [{ botId: lead, reason: 'lead' }]   ← 新增
否则                                      → triage 广播判断（现有）
```

- `DispatchTarget.reason` 增 `'lead'`；协调器依赖里增 `leadOf(conversationId)`（同 `#activeMembers` 的注入方式）。触发段文案带「用户消息默认交给你（项目负责人）」，让负责人知道自己为什么被唤醒，并可 `skip_reply`。
- 有负责人时**不再出现** triage 阶段（状态行「正在确认由谁回复」）与 `group_no_claim`；成员数 N 的群每条消息省下 N 次轻量调用。
- 用户 `@` 成员或回复成员的消息只到该成员，**不**同时唤醒负责人（成本）；负责人在下一次被唤醒时从群历史看到。
- 轮次内新到的批仍按现有规则排队，不 steer 进行中的 Bot（02「群聊响应」第 6 条不变）。
- **D5 修订（拟）**：「未指定时全员判断、按序响应」只适用于无负责人的群。

**负责人调度成员的链路（本期）**：用户 → 负责人（链深 0）→ `@` 成员（深 1）→ 成员完成后 `@` 负责人汇报（深 2）→ 负责人汇总回复用户。设计意图是落在现有预算内（深度 ≤ 3、200k token）。

**已核实的缺口（读代码得出）**：成员的对话轮常常只是「我去做」并 `start_task`，任务结算经 TaskHost 的 `wake` 回调（`dispatch/orchestrator.ts`）以 `reason:'task'` 的批次唤醒成员的下一个对话轮。该批次**不带** `chain`；`#startTurn` 只在 `batch.chain` 存在时才给 run 绑 `chain_id`，任务 run 自身也不绑连锁。于是这一轮再 `@` 负责人汇报时，`ChainsService.mention` 读到 `chainId = null`，会**新开一条连锁，深度重新从 1 算起、预算重新给 200k**。后果：只要中间隔一个任务，D4 的深度与预算上限就被重置，「负责人 → 成员（任务）→ 汇报 → 再派 → …」在宿主层面没有上限，任务用量也不计入任何连锁预算。这个缺口今天的群聊里就存在（Bot A `@` B、B 派任务、结果轮再 `@` A……），负责人式调度会让它从偶发变成常态。

**拟定修法（并入 T1.4，需你确认，Q6）**：任务结算唤醒的对话轮沿任务的 `origin_run_id` 继承原连锁——`wake` 时取 origin run 的 `chain_id` / `chain_depth` 放进批次的 `chain`；并把任务 run 也绑到该连锁，使深度与 token 预算覆盖「对话轮 + 任务」。这是对 D4 / D75 连锁语义的修订（现行只覆盖对话轮），改动集中在 `wake` 回调、任务 run 创建与 `ChainsService` 的用量统计。代价：任务通常比对话轮贵得多，`BOT_CHAIN_TOKEN_BUDGET`（200k）对带任务的连锁可能过紧，需要重新评估（折算任务用量或单列任务预算）。不修的话，最低限度在负责人提示词里写「一次用户请求最多往返 N 次」作软约束——但那只是提示词，不是宿主强制。

深度上限 3 是否够用，本期沿用现有常量，收集真实用法后再议。

## 6 模块框架

### 6.1 注册表（`packages/shared`，纯数据，写法同 `HOST_CAPABILITIES` / 设置目录）

```ts
export const TEAM_MODULES = [
  { id: 'chat',     status: 'available', write: 'members' }, // 沟通：全员可发言
  { id: 'board',    status: 'planned',   write: 'lead' },    // 看板
  { id: 'docs',     status: 'planned',   write: 'members' }, // 文档
  { id: 'okr',      status: 'planned',   write: 'lead' },    // OKR

// 读权限恒为「项目组全员」；用户恒可读写；标题等文案走渲染层 i18n（`team.module.{id}`）
```

- 渲染层 tab 顺序与灰显状态读此表；`planned` 灰显并提示「即将推出」。
- 纯函数 `canWriteModule(moduleId, actor: 'user' | 'lead' | 'member')`（shared）+ 表驱动单测。**本期暂无调用方**（只有沟通），先把契约与测试定下来，第一个写模块接入时启用。
- **明确不做**：宿主侧的 `contextSection` / 工具注册 / 服务生命周期等插件接口。只有一个模块时抽象出来的形状大概率是错的；由看板（T2）驱动落地，再回头把共性提进框架。

### 6.2 宿主强制原则

- 模块工具在**执行处**校验：调用者是否为负责人（`conversations.lead_bot_id === identity.botId` 且 `identity.conversationId` 是该组）并调用 `canWriteModule`；失败返回结构化错误，不靠提示词劝阻。
- 负责人工具只在对话轮的工具面注册（同 D75：对话轮「立即返回、宿主干活」的托管动作），任务面不注册。
- **与 D90「仅用户本人触发」闸门的关系**：管家被该闸门限制，是因为它权力全局、半夜替用户派活是越权。负责人的职责本身就是在项目内自动调度（成员汇报会唤醒它，那一轮不是「用户本人触发」），套同一闸门等于废掉这个角色。所以拟定：**项目内操作（**`@` **成员、写看板 / OKR）不设此闸门；项目外一概无权**。代价是项目内多了一条「成员读到恶意网页 → 汇报污染负责人 → 负责人被诱导派活」的传播链，缓解见 §6.3 与 §11。这是方案里最需要评审的取舍（Q5）。

### 6.3 渐进披露与信任分级（框架约定，下期模块遵守）

- **可见 ≠ 全量注入**：每个模块提供一段 ≤ 500 字的摘要（计数 + 要紧条目）进群聊系统提示，细节经只读工具按需取（对照 `<workbench>` 与 `list_todos`）。
- **按写入者标注可信度**：用户写入的内容可信；负责人 / 成员（Bot）写入的内容，其他 Bot 读取时包进 `<untrusted source="team:{moduleId}">`（同 D90 对管家起草内容的处理）。共享可写的文档模块尤其如此。
- **读过外部内容的一轮**收紧写权限的判据沿用 D89 的 `touchedUntrusted`，具体到每个模块的写工具时再定。

### 6.4 下期模块与现有机制的衔接（预研，不在本期实现）

| 模块 | 现有机制 | 建议方向 | 先要回答的问题 |
|---|---|---|---|
| 看板 | D90 `todos`（状态 draft → scheduled → in_progress → delivered → done 与看板列天然对应）、D75 任务、`dispatchWorkbenchMessage` | 给 `todos` 加项目组范围，看板 = 该项目组事项的列视图；工作台自然汇总所有项目的事项；指派卡片 = 沟通里一条派发消息，复用交付追踪 | D90「普通 Bot 不能操作事项」要放宽为「负责人可操作本组事项」；成员能否改自己卡片状态（建议由交付追踪推进） |

## 11 风险与取舍

1. **写入租约让成员串行写目录**：同一 workdir 同时最多一个写任务（D75，明确不做 worktree）。项目组里多个成员同时改同一目录会排队。本期无变化，但这是「项目协作」价值感的最大瓶颈，看板指派并行任务时会放大；缓解口子只有 `task_workdir`，需单独讨论，不在本期。
2. **负责人成单点**：未 `@` 的消息都进负责人，它的模型质量、上下文长度、成本成为瓶颈；用户可随时 `@` 成员绕过；无负责人时回落广播。
3. **行为变化**：群聊从「大家听、各自判断」变成「负责人先接」。已习惯旧体验的用户可能不适应；是否提供「广播模式」开关见 Q2。
4. **连锁防环有缺口（已核实）**：任务结算唤醒的对话轮不继承连锁，隔一个任务就重置深度与预算（§5.3）；负责人调度会把它从偶发变常态。修法会改 D4 / D75 的连锁语义，且任务用量计入后 200k 预算可能偏紧。
5. **项目内自动化的提示注入**：成员读恶意内容 → 汇报污染负责人 → 诱导派活。缓解：权力半径 = 项目组（项目外的审批、沙箱、敏感写入闸门不豁免）；Bot 写入内容读取时标 `<untrusted>`（§6.3）；`@` 链有深度与预算。这是缓解不是消除。
6. **撤右栏的回归**：授权撤销可达性、成员浏览器按钮、定时 / 监看列表要全部迁移并有 e2e；`GroupSettingsDialog` 的 `embedded` 入口被设置卡依赖，改造时不能破坏。
7. **新成员静默获得目录读写**：靠 §5.5 的系统消息补；更严格的做法（加入前确认）暂不做。
8. **命名**：「项目」「任务」「组队」三处撞名（§2.3），文案改动面大但可控——key 与 testid 不动。
9. **本期无负责人专属能力**：只有默认路由与提示词，价值要靠下期模块兑现。若觉得本期交付感不足，可把「负责人维护项目目标」提前，但它属高敏感写（§6.4），需要先定闸门。
