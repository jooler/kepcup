# 01 对话模型

## 通讯录

- 用户添加的 Bot 出现在通讯录中。
- 删除对话不影响通讯录，Bot 依然存在。

### 删除 Bot

与微信删除联系人类似：历史消息都在，但 Bot 不再可用。

- 删除前**弹框提醒**：列出将被清理的内容（记忆、Wiki、Skills、workspace 的数量），并说明不可恢复。
- 私聊对话保留，转为**只读**；Bot 名称显示为其 id；该对话的待发送队列清空。用户仍可删除该对话。
- 在群中：从成员中移除，不能再被 @；历史消息保留，发送者显示为其 id。
- 与该 Bot 相关的所有 loop（响应与后台）立即中断并停止，队列清空，定时任务取消，待确认的环境申请作废。
- Bot 数据的清理与保留见 [03-bot.md](03-bot.md#生命周期)。

## 单聊

- 与微信一致：用户与每个 Bot 只有一个对话，所有历史在该对话中累积。
- 用户可以删除对话，删除后对话从列表和历史中消失。再次发消息时开启一个新的对话实例。

## 群聊

- 用户在一个群中与多个 Bot 对话，由 Bot 按需响应。响应规则见 [02-execution.md](02-execution.md#群聊响应)。
- 群定位（本群主要处理什么事务）在创建时以对话内问答收集，存于对话的 `description` 并注入群内 Bot 的上下文；创建流程见 [19-work-path-and-group-setup.md](19-work-path-and-group-setup.md)。

### 成员变动

- **移除 Bot**：直接移除，不能再被 @。该 Bot 在此群中进行中的 loop 中断，在此群的定时任务取消、承诺作废，在此群的 workspace 删除。历史消息保留，发送者仍显示 Bot 名称。
- **新增 Bot**：状态与它一直在群中一样。被调用时可以通过查询工具读取完整的群历史，正确获取上下文。它在此群的 workspace 在首次执行时新建。

## 对话 id

- 每一个对话实例拥有全局唯一的 id，**删除后永不复用**。
- 这样删除后的新对话不会落入旧 workspace、看到旧文件。

## 对话与执行分离

- 对话只记录和展示双方交流的消息。
- Bot 的执行过程（工具调用、中间步骤）存放在执行记录（Run）中，不混入对话。
- Bot 可以通过工具按条件查询对话内容，见 [02-execution.md](02-execution.md#上下文注入)。
- 跨 Bot 委派（D71）会在**被委托方**私聊中插入带 `origin=delegation` 标签的用户代发消息（「由 A 代你发出」），并把截断后的终回复以卡片贴回委托方对话；UI 默认留在委托方。详见 [27-butler-and-delegation.md](27-butler-and-delegation.md)。

## 输入与待发送队列

用户自己决定何时把消息发给 Bot，不做基于等待时间的防抖。

| 操作 | 结果 |
|---|---|
| 输入框有内容时触发发送（发送按钮或 Enter） | 内容进入**待发送队列**，在界面中可见，输入框清空 |
| 队列有内容且输入框为空时触发发送 | 队列全部发出，并唤醒 Bot |
| 继续输入并触发发送 | 新内容追加到队列末尾 |
| `Cmd/Ctrl+Enter` | 当前输入追加到队列并立即全部发出 |

- 队列中的内容是本地草稿，Bot 看不到；发出前可以修改、删除、调整顺序，关闭应用后仍保留。
- 附件也可以进入队列。
- 附件的上传链路、媒体内联渲染与模型生成媒体见 [20-conversation-media.md](20-conversation-media.md)。
- 发出时，队列中每一项成为一条独立消息；这一批消息只触发一次 loop，执行记录中记录多条触发消息。
- 群聊中，这一批消息里的所有 @ 合并计算。
- Bot 执行期间用户可以照常向队列写入；发出后的消息在 loop 的下一步注入。

## Project

- 右栏「配置」tab 内有 project 选择器（群聊在群信息面板），选择一个本地目录作为该对话的 project。
- 选定后，该对话中所有 Bot 都可以读写该目录，并以它作为默认工作目录。
- 详见 [08-project.md](08-project.md)。

## 消息模型

```text
Message
  id
  conversation_id
  seq                 -- 对话内单调递增序号
  sender              -- user | bot:{id} | system
  type                -- text | image | file | system_event ...
  content
  reply_to            -- 引用回复的消息 id
  mentions[]          -- 被 @ 的 Bot
  attachments[]
  status              -- normal | recalled | edited
```

- 群聊中每条消息都带明确的发送者标识，避免 Bot 把其他 Bot 的发言当成自己的。
- 文件在各方之间以消息附件的形式传递，附件存放在对话级存储中。
- 系统消息用于展示事件，例如“所有 Bot 都未响应，请指定一个 Bot”（附可点击的 Bot 列表）。

### 消息原则：Bot 的内部事务不进对话

Bot 类似一个真人：用户交代任务，怎么执行、怎么积累经验（记忆/反思）、怎么整理自己的知识库（Wiki）、怎么管理自己的运行环境（组件安装）与技能，都是 Bot 自己的事务，**不以系统消息形式向用户报告**。

- wiki 入库/体检、环境安装的批准记录与进度、技能导入、凭据处理、调度触发等，只作为**内部事件**写入消息存储（`system_event` + `internal: true`，事件名清单见 shared 的 `INTERNAL_SYSTEM_EVENTS`）：照常进入 Bot 的上下文并触发其行动，但用户可见的消息流（`messages.list`、`message.created` 推送）把它们过滤掉。
- 对话里只出现三类内容：用户与 Bot 自己的话；需要用户参与的事件（审批卡、初始化访谈、群聊无人认领提示）；影响用户任务状态的事实（执行被中断等）。

## “像真人”的交互表现

- 执行期间对话中显示“正在处理”状态，并支持已读。
- 一次 loop 可以发送多条消息：先确认收到，中途同步进展，最后交付结果。中间进展主要来自“带工具调用的回复”里的说明文字（自动投送，见 [02-execution.md](02-execution.md#bot-如何发消息)），不依赖模型自觉调用 `send_message`。
- 消息整条发送，不做逐字流式输出。
- “正在处理”状态行排在消息流末尾（即下一条消息会出现的位置），以绿点与状态文字显示当前活动（请稍等… / 正在调用工具 X…）；本 Bot 的新消息落库时状态行让位消失，下一个工具活动再出现，如此交替直到最终回答（见 [12-ui-layout.md](12-ui-layout.md#焦点二消息流末尾)）。
- 长任务、失败、超时在对话中有对应的消息表达；用户可以取消正在执行的任务。

## 删除对话

删除对话时一并删除：

- 该对话的消息
- 该对话的执行记录
- 该对话下所有 Bot 的 workspace
- 该对话的附件
- 绑定到该对话的定时任务

作废：

- 在该对话中做出的承诺

保留：

- 各 Bot 的其他长期记忆
- 共享用户画像
- 各 Bot 的 Wiki（包括从该对话入库的资料）与 Skills
