# 周报 / 日报

产出一篇**向上汇报**的状态更新。核心是让读者 1 分钟内知道：事情推到哪了、有什么风险、需要他拍板什么。

## 模板

```markdown
# 周报 {姓名/团队} {YYYY-MM-DD ~ MM-DD}

## 本周进展
1. {事项}：{结果/进度%}（对比目标：{正常/滞后/提前}）
2. ...

## 关键数据
| 指标 | 本期 | 上期 | 环比 | 备注 |
|---|---|---|---|---|

## 问题与风险
- {风险} → 影响：{...}；需要：{支持/决策/资源}（负责人 {…}）

## 下周计划
1. {事项}（预计完成 {MM-DD}）

## 需要你拍板
- {明确的请求，没有就写"无"}
```

日报用同一结构，删去"下周计划"或改为"明日计划"。

## 素材来源

- 用户丢来的素材（聊天记录、笔记、文档）是第一来源；引用时保留原始数据口径。
- 用户明确允许时，可参考 Bot 的 wiki/记忆里既往周报，保持指标口径与格式连续：**同一指标本期上期必须同口径**，口径变了要备注。
- 素材不足以填某节时，明确写"待补充"并单独列出缺什么，**不要编造数据**。

## 写作标准

- 结论先行：每条进展一句话讲完"做成了什么、到什么程度"，过程细节折叠在后面。
- 量化：能上数字的都上数字（进度%、完成量、环比）；"基本完成""顺利推进"这类空话禁止。
- 风险诚实：滞后的事项写滞后及原因，这比藏住更专业；每条风险带"需要什么支持"。
- 篇幅：周报 ≤ 400 字正文 + 数据表；读者是上级，不是存档。
- 语气：平实书面语；公司有固定格式/系统（如飞书表格）时先问模板。

## 交付

默认输出到对话方便用户改；用户要文件时存工作区 `周报-{YYYY-WW}.md`。完成后问一句：是否需要按上周格式调整。
